# Cyber Garden 2026 — правила работы над проектом

Платформа позволяет собрать визуальный сценарий проверки учебного Kotlin-проекта, запустить свои анализаторы и получить отчёт с AI-рекомендациями. Проверяем только репозитории организаторов и собственные безопасные учебные проекты. Целевой проект использует Kotlin, Spring Boot и Gradle Kotlin DSL.

## Стек и границы MVP

Стек бэкенда — Python + FastAPI и PostgreSQL. Для фронтенда предлагаем React + TypeScript + React Flow. Бэкенд приложения и исполнитель сценариев могут жить в одном сервисе. DeepSeek — первый внешний провайдер LLM, локальная модель подключается через тот же интерфейс.

В обязательном сценарии пользователь загружает файлы или указывает ссылку на разрешённый учебный репозиторий, собирает граф, запускает его и видит статусы и результаты по нодам. Добавляем ручной запуск и расписание, условие со сравнениями и regex, три своих анализатора, AI-рекомендации и один канал уведомлений. Для первого демо используем HTTP webhook.

Регистрация, сохранение своих сценариев и настроек входят в интерфейсный план команды. Для пункта «Скачать» в меню «Файл» предлагаем экспорт схемы сценария в JSON. Перестановку панелей можно добавить после рабочего прогона. Публичную библиотеку шаблонов, запуск из CI/CD и генерацию сценария по промпту берём после основного сценария. Каталог нод — список доступных типов, «Мои сценарии» — сохранённые пользователем графы. Если понадобятся сохранённые пресеты отдельных нод, обсудим их отдельно.

## Общий контракт v0

Фронтенд и бэкенд обмениваются JSON с полями в `camelCase`. ID — непрозрачные строки. Номера строк начинаются с 1, пути относительны корня проекта и используют `/`.

```ts
type NodeType = 'trigger' | 'secrets' | 'sca' | 'sast' | 'condition' | 'ai' | 'notify'
type RunStatus = 'queued' | 'running' | 'succeeded' | 'failed'
type NodeStatus = RunStatus | 'skipped'

interface Workflow {
  id: string
  name: string
  nodes: Array<{
    id: string
    type: NodeType
    position: { x: number; y: number }
    config: Record<string, unknown>
  }>
  edges: Array<{
    id: string
    source: string        // ID исходной ноды
    target: string        // ID следующей ноды
    sourceHandle?: 'true' | 'false' // Только для выхода condition
  }>
}

interface Finding {
  id: string              // Уникален в пределах запуска
  scanner: 'secrets' | 'sca' | 'sast'
  ruleId: string
  file: string
  line: number | null     // null, если точная строка неизвестна
  severity: 'low' | 'medium' | 'high' | 'critical'
  message: string
  cve?: string            // Из справочника, если указан
}

interface AiAnalysis {
  summary: string
  recommendations: Array<{
    findingId: string
    explanation: string
    remediation: string
  }>
}

interface RunReport {
  runId: string
  workflowId: string
  status: RunStatus
  nodes: Array<{
    nodeId: string
    status: NodeStatus
    output?: Record<string, unknown> // Очищенный результат ноды
    error?: string
  }>
  findings: Finding[]
  aiAnalysis?: AiAnalysis
}
```

### Как соединяются ноды

| Тип | Вход и настройки | Выход |
|---|---|---|
| `trigger` | `config.mode` — `manual` или `schedule`. Запуск получает `sourceId` загруженного проекта. Планировщик использует `config.sourceId` и `config.schedule` | `{ sourceId }` |
| `secrets`, `sca`, `sast` | `sourceId` из контекста запуска. Каждая нода добавляет результаты своей проверки | `{ findings: Finding[] }`. Пустой список означает успешную проверку без находок |
| `condition` | Находки из предыдущих нод. Первое правило принимает `config.minSeverity` и проверяет, есть ли находка с такой или большей критичностью. Остальные сравнения и regex уточняются отдельно | `{ matched: boolean }`. Активируется выход `true` или `false` |
| `ai` | `findings: Finding[]` из активных входов | `AiAnalysis` после валидации |
| `notify` | Находки и `aiAnalysis`, если она есть. Адрес webhook берётся из защищённой настройки `config.webhookRef` | `{ delivered: boolean }`. Ошибка доставки видна в статусе ноды |

Для v0 граф имеет один триггер, циклы запрещены. Контекст передаётся по активным связям. Анализаторы добавляют находки к полученному списку, условие передаёт его в выбранную ветку, AI добавляет рекомендации. Нода с несколькими входами ждёт завершения всех входящих веток и объединяет находки по `id`. Если активных входов нет, нода получает `skipped`. Ошибка ноды делает итоговый статус прогона `failed`. Если провайдер LLM недоступен, нода `ai` передаёт дальше найденные проблемы, а `notify` отправляет их без рекомендаций. Форматы расписания и остальных сравнений согласуют фронтенд и бэкенд до реализации соответствующих форм.

### Первый API для стыковки

Текущий бэкенд поддерживает локальный режим с одним общим рабочим пространством, загрузку ZIP, сохранение графов, ручные запуски, `secrets` и `condition` с `minSeverity`. Остальные типы нод можно сохранять в графе как черновик. При попытке запуска неподдерживаемой ноды API вернёт `422 unsupported_node`. Инструкция запуска и пример запроса есть в [BACKEND.md](BACKEND.md).

| Запрос | Результат |
|---|---|
| `POST /sources` | Принимает `multipart/form-data` с архивом в поле `file` или JSON `{ repositoryUrl }` со ссылкой на разрешённый учебный репозиторий. Возвращает `{ sourceId }` |
| `GET /workflows` | Возвращает собственные сохранённые сценарии пользователя |
| `POST /workflows` | Принимает `Workflow` без `id` и возвращает сохранённый `Workflow` |
| `GET /workflows/{workflowId}` | Возвращает `Workflow` |
| `PUT /workflows/{workflowId}` | Обновляет и возвращает `Workflow` |
| `POST /workflows/{workflowId}/runs` | Принимает `{ sourceId }` и возвращает `{ runId, status }` |
| `GET /runs/{runId}` | Возвращает `RunReport`. Фронтенд может опрашивать этот ресурс для отображения выполнения |

Для ошибок API фронтенд ориентируется на HTTP-статус и тело `{ code, message }`. Эндпоинты аккаунтов, расписания, настроек провайдера и AI-чата добавляем в этот раздел до их реализации. Чат MVP работает с выбранным отчётом и вопросом пользователя. Генерация редактируемого графа по промпту остаётся задачей со звёздочкой.

## Правила для участников и ИИ-инструментов

- Перед правками прочитай этот файл и существующий код. Делай только назначенный модуль. Для стыковки используй согласованный контракт и тестовые JSON, пока соседний модуль в работе.
- Изменения полей, значений enum, маршрутов и поведения исполнителя сначала согласуй с владельцами затронутых модулей. Обновляй контракт вместе с реализацией. Для согласованных API используй OpenAPI FastAPI как машиночитаемое описание.
- Поиск секретов, SCA и SAST реализуются своими правилами. Готовые сканеры, их движки и чужие наборы правил запрещены ТЗ. Анализируй входные файлы как данные. Поиск уязвимостей остаётся за сканерами при любом состоянии LLM.
- В LLM передавай структурированные находки, очищенные от значений секретов. Проверяй структуру ответа и принадлежность `findingId` текущему запуску. Файлы, строки и CVE для отчёта берутся из исходных находок. Отклоняй рекомендации с выдуманными ссылками на файлы, строки или CVE. Ошибка LLM сохраняется отдельно, исходные находки доступны в отчёте.
- Ключи LLM, токены и секреты каналов уведомлений остаются на бэкенде. В граф, UI, логи и отчёт попадают только безопасные ссылки на настройки и маскированные значения.
- Сначала проверь свой модуль на синтетических данных и один стык с соседним модулем. Зафиксируй, что реализовано и какой сценарий удалось прогнать.

## Первый командный прогон

1. Бэкенд и фронтенд собирают ручной сценарий `Запуск → Поиск секретов → AI-рекомендации → Уведомление` и стыкуются по тестовому JSON.
2. Дизайнер описывает состояния этой цепочки от пустого редактора до отчёта и ошибки. Разработчик LLM проверяет `Finding → AiAnalysis` сначала на заглушке, потом с DeepSeek.
3. Команда прогоняет цепочку на синтетическом проекте или репозитории организаторов, затем добавляет SCA, SAST, ветвление и расписание.
